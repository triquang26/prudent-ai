One-paragraph summary

Companies pick AI models for real tasks — a support chatbot, a medical assistant — using public benchmark scores. We collected every usable public measurement we could find (20 sources, 5,164 measurements) and asked, for thousands of realistic “which model should I deploy?” decisions: can the available evidence actually answer this? 91% of the time, it can't. Worse, the standard practice of picking the cheapest model that looks good enough silently breaks a stated requirement 57% of the time. We built a decision procedure that only answers when it can prove the answer — it was correct in 527 out of 527 such decisions — and when it can't, it refuses and names the single cheapest measurement that would unblock the decision.

The problem

A question every team asks, and the evidence rarely answers

Imagine a hospital deploying a patient-support chatbot. The team writes down what they actually need:

  1. Answers must be good enough — at least 80% acceptable.
  2. Replies must arrive within 2 seconds.
  3. Each query must stay within a per-query budget.
  4. The system must satisfy healthcare compliance rules (HIPAA).
  5. The clinical staff has limited capacity to review the bot's answers.

Then they ask the obvious question — the one this whole project is about: “What is the smallest, cheapest AI setup that still meets all five requirements?” We call that the right-sizing question. Today, teams answer it by looking at public leaderboards and picking the cheapest model whose visible scores look good.

Here is the catch we found when we assembled every usable public measurement — 20 benchmark sources covering quality, speed, price, energy, safety, even medical tasks: for requirements like compliance and staff review workload, there are zero measurements. Anywhere. Not one of the 20 sources — including the safety leaderboards and the clinical benchmark — measures whether a deployment meets an organization's rules. The hospital's question is not hard to answer. It is impossible to answer from the evidence that exists.

The one-sentence thesis: the first property to check about an AI deployment decision is not which option is best, but whether the evidence can answer the question at all — and most of the time, it can't.

Key findings

Three things we can now say with evidence

1Most deployment decisions are unanswerable

91.1%

We generated thousands of realistic deployment questions — combinations of real requirement profiles (chatbots, copilots, medical assistants…) with real constraint levels — and checked each one against the full 20-source evidence pool. For 91.1% of them, the combined public evidence of the field cannot identify the cheapest adequate option. This isn't because models are bad; it's because the measurements that would settle the question were never taken.

2Answering anyway silently breaks things

57.1% → 0%

Standard practice doesn't stop at unanswerable questions — it picks the cheapest model that looks good on the visible numbers. On 476 decisions where we know the true answer, that practice shipped a configuration that silently violated a stated requirement 57.1% of the time. “Fill in the blanks with a typical value” strategies failed at exactly the same rate — when a requirement is measured nowhere, any filled-in value is invented. Our procedure's silent-violation rate on the same decisions: 0% (statistically decisive, p ≈ 0).

3Refusing well: name what to measure

527/527

A refusal is only useful if it comes with a next step. When our procedure does answer, it has been verified correct in all 527 of 527 decisions (provably cheapest option that fits, zero hidden violations). When it refuses, it names the single missing measurement most worth taking — and following that advice unblocked a correct decision 100% of the time, versus 12.9% for measuring a randomly chosen missing quantity. And it carries a calibrated guarantee: allowed a 5% error budget, its actual error stayed at 4.7–4.9% on held-out ground truth.

The refusal is the feature, not the failure. Each refusal is a proof that the question is unanswerable as posed, plus the cheapest concrete step that makes it answerable. That converts “we don't know” from a dead end into a measurement plan.

How it works, A → Z

From raw leaderboards to a provable decision

Nothing here is a black box. The whole system is four stages, each one inspectable in the repository — this section walks through all of them: how the data is organized, how the database schema links together, how real deployments become precise questions, and exactly what the decision engine computes.

Step 1 — Organizing the world's evidence into one database

The database has three linked tables. Keeping measurements in their own table — instead of one spreadsheet row per model — is the design decision the whole project rests on: it lets one model×requirement pair hold several measurements from different sources, and lets an empty pair stay honestly empty.

Here is what one real row of the OBSERVATIONS table looks like, and how it links outward:

one observation record (real structure) 
observation
  configuration : "gpt-4 @ api"            → links to CONFIGURATIONS
  requirement   : quality                  one of the 8 requirement types
  value         : 0.85                     kept on its native 0–1 scale
  confidence    : H                        measured first-hand (see grades below)
  source        : "RouterBench"            → links to SOURCES = full provenance
  context       : dataset=mmlu · split=test · date=2023-11

Every incoming number gets a confidence grade, assigned by a fixed rule — never by judgment call:

How the number was obtainedGradeTrusted by default?
Measured first-hand, methodology fully disclosedHighyes
Read off a public leaderboardMediumyes
Reported in a paper, raw data not releasedMediumyes
Back-estimated from a paper's figureLowkept, but excluded
Vendor marketing documentationLowkept, but excluded

The normalization rules (the “feature extraction”)

  • One unit system. Quality on its native 0-to-1 scale; price in USD per query; speed in seconds; energy in watt-hours. A source using a different scale (e.g. 1-to-5 jury ratings) is skipped and logged, never rescaled — zero corruption events across all 20 sources.
  • No silent upgrades. If a source reports an average where a worst-case is needed, it's recorded at lower confidence — never converted or pretended.
  • Deterministic identity. Each record's ID is computed from (configuration, requirement, evidence source) — so re-running ingestion is idempotent: no duplicates, ever.
  • The never-fill-in rule. An empty cell stays empty. The engine reasons about absence; it never papers over it. This single rule is what separates the approach from everything in the comparison section.

Step 2 — Turning real deployments into precise questions

A question = a task family + a list of requirement bars (quality ≥ 0.8, speed ≤ 2s, …). We didn't invent the questions: they come from 1,716 real-world deployments in a public database of industry case studies, each translated by a fixed dictionary — and each bar sits at the median observed value for its task family, so it's demanding but real. Tags with no clear requirement signal add nothing — we'd rather understate the problem than invent constraints.

What those 1,716 real deployments actually require: 100% constrain quality, 47% response speed, 41% price — and 56% constrain compliance and 44% review workload, the two requirements with zero public measurements anywhere. That overlap is why the 91.1% headline is about real traffic, not a constructed worst case.

Step 3 — Inside the decision engine

The engine never works with point guesses. For every candidate and every requirement it gathers all trusted measurements in that cell and summarizes them as an interval — worst seen to best seen. Proof then means: the whole interval clears the bar. One picture explains the whole idea:

The same logic, written out — this is the complete algorithm, nothing omitted:

the decision engine — complete logic, nothing omitted 
# Pass 1 — classify every candidate configuration
for each candidate x:
    for each requirement (type, bar):
        evidence  = all trusted measurements in cell (x, type)
        interval  = [worst seen, best seen]
        if no evidence                     → type is UNKNOWN for x
        elif whole interval clears the bar → requirement PROVEN
        elif whole interval misses the bar → requirement BROKEN
        else (interval straddles the bar)  → type is UNKNOWN for x
    x is PROVEN-FIT   if every requirement PROVEN
    x is PROVEN-UNFIT if any  requirement BROKEN
    x is UNKNOWN      otherwise — carrying its list of unknown types

# Pass 2 — decide at the level of the whole question
if every x is PROVEN-UNFIT → NOTHING FITS (with the proof)
pick = cheapest PROVEN-FIT x          # judged on its worst-case price

# Pass 3 — the flip test: is the pick PROVABLY best?
if any UNKNOWN x could, resolved favourably, undercut pick:
    → REFUSE; blocking = that x's unknown types
    → rank each blocking measurement by (regret it removes ÷ cost to measure)
    → name the top one                # "measure compliance first"
else:
    → DECIDE pick                     # correct in 527/527 verified cases

How a refusal turns into a measurement plan

Each blocking measurement is scored as value ÷ cost: the value is the unavoidable regret it removes — exactly the $\delta\lambda/(\delta+\lambda)$ quantity from the theory section — and the cost reflects how expensive that measurement is in practice. The engine uses a fixed relative cost table: a price lookup is the cheapest check; a speed test ~2× that; a quality evaluation ~6×; and a compliance audit ~20× — the most expensive thing you can be forced to measure. The named recommendation is the top of this ranking, which is what beat random advice 100% vs 12.9%.

One honesty knob completes the engine: the error budget. The engine only decides when its pick beats the runner-up by a safety margin; the margin is calibrated on half the ground truth, tested on the other half — that's the 4.7–4.9% realized error at a 5% budget.

Finding 2 — deciding anyway breaks things silently

The numbers

  • Standard practice: 57.1% silent violations — three independent variants of it, identical rate
  • Our procedure: 0.0% on the same 476 decisions
  • Cases where ours did worse: 0; significance p ≈ 0
  • Holds in each of 28 scenario slices tested, individually significant
  • Control slices where guessing is actually safe: violation rate correctly drops to zero — the test discriminates, it doesn't just always fire

Why “just fill in the blanks” can't fix it: imputation strategies produced byte-identical choices to plain guessing — the requirements that block these decisions are missing everywhere, so any filled-in value is invented, and the invented value is what gets violated.

The price-of-removal test

For every refusal, we checked: if you delete the requirement our procedure says is blocking, does the decision become answerable? Across 544 decisions: agreement 1.00, zero exceptions. The procedure isn't refusing vaguely — it points at exactly the constraint that binds.

Finding 3 — the procedure earns trust in both directions

a) When it decides, it's right

Across every ground-truth slice where a decision is provable: 527 of 527 decisions correct — each pick truly meets all requirements and is the genuinely cheapest one that does. Verified three independent ways, including a mirror test: hide the key measurement and the same 527 decisions all flip to refusals — it decides exactly when it can see, never when it's blind.

b) Its “measure this next” advice works

Following the procedure's named measurement unblocked a correct decision 100% of the time (527/527); measuring a random missing quantity instead: 12.9% — about 1 in 8.

The blind spot survived our best attempt to kill it

We specifically went looking for compliance and review-workload evidence: we ingested the safety leaderboards and a clinical benchmark suite, expecting them to cover it. Still zero. Safety benchmarks measure whether a model says harmful things — not whether a deployment satisfies an organization's rules. Those are different questions, and the second one is unmeasured industry-wide.

Data hygiene: every quality score is kept on its native 0-to-1 scale; anything off-scale is skipped and logged, never rescaled or guessed (zero corruption events across all 20 sources). Where a source reports an average instead of a worst-case, we record it as lower-confidence rather than pretending otherwise. A missing value stays missing — the system never fills one in.

Why it's unavoidable

The theory, in one minute

Suppose two configurations look identical on everything measured, and differ only on a requirement nobody measured — say, compliance. Then two worlds are perfectly consistent with all the evidence: one where the cheaper option complies (pick it!), one where it doesn't (picking it is a violation). No algorithm, however clever, can tell these worlds apart — the information simply is not in the data. Any committed choice must be wrong in one of them.

The best achievable expected loss when forced to choose is exactly

$\text{unavoidable regret} \;=\; \dfrac{\delta\,\lambda}{\delta+\lambda}$

where $\delta$ is the price difference between the two options and $\lambda$ is the cost of shipping the violating one.

Two consequences, both verified empirically above: (1) the value of taking the missing measurement equals exactly that unavoidable regret — and our procedure's computed measurement-values match this formula to 19 decimal places; (2) a decision is answerable precisely when every requirement that actually constrains it is either measured, or derivable from something measured. That's a clean characterization, not a heuristic.

Honestly flagged sharp edges: (1) the guarantee is calibrated on the question distribution we constructed, not on “all possible questions”; (2) a few theory checkpoints await an independent human verification pass; (3) some evidence sources (one gated API, paper-table extraction requiring two human annotators) were skipped, not approximated — the pool only contains what could be ingested mechanically and exactly.

Reproducibility

Built so a skeptic can check everything

Engineering discipline

  • 73/73 automated tests pass, including one that proves the core data-access interface never changed during the project
  • All headline numbers come from frozen, committed result files — the page you're reading contains no number that isn't in the repo
  • Every run is described by a single seeded config file — re-running reproduces results bit-for-bit
  • Calibration and evaluation use a strict 50/50 split — no leakage; ground-truth scores are never used for tuning

Research discipline

  • The whole project is a version-controlled experiment graph: every experiment is a node with its success criteria written down before running
  • An independent adversarial review pass attacked the claims; its objections and their resolutions are committed in the repo
  • Negative controls throughout: the sanity checks that should fail, fail (see the 12.4% collapse in the robustness table)
  • Anything requiring human judgment was skipped, not approximated — and labeled as such
